# 抱布记项目综合审查

日期：2026-10-28。代码基线：`2d57fa0`，分支 `main`。

## 1. 总体结论

**产品方向适合继续，技术栈适合当前自用规模，现有实现适合作为基础原型；尚不具备“可靠自动收集私人生活素材”的可用版本条件。建议渐进完善，不推倒重写。**

最明显的问题是开发重心与用户价值尚未闭合：身份、限流、迁移预检已有多轮隔离验证，但用户还不能在产品内完成来源连接、看到采集进度、管理真实照片或文字，也不能从完整历史中偶遇回忆。继续无限增加底层原语，会推迟真正的体验反馈。下一步应以一个可验证的端到端使用场景组织工作。

同时不能因为基础测试通过而直接上线。当前有可以绕过部署保护的入口、测试导入应用时的数据库副作用，以及删除恢复语义、客户端失效会话处理等实际缺口。先修复这些边界，再开通受控真实数据试用。

### 分项判断

| 方面 | 判断 | 修改方向 |
|---|---|---|
| 用户需求 | 目标清晰，自动采集、私人空间、偶遇普通瞬间相互一致 | 将“尽可能自动”转为有范围、有状态、有恢复路径的承诺 |
| 首版范围 | 高驰、安卓、照片存储、微信身份同时完整上线过大 | 先高驰摘要闭环，再照片闭环；照片仍是完整首版组成部分 |
| 交互 | 星空光点可作探索入口，现阶段主要是文本卡片和最近列表 | 提供日期跳转、详情、管理和全历史偶遇，保留常规列表 |
| 技术栈 | 原生小程序 + FastAPI + SQLite 可继续用 | 模块化单体，独立 worker；暂不拆微服务或换前端框架 |
| 数据模型 | 最小文本模型足以验证列表，不足以承载照片和来源生命周期 | 增加来源连接、媒体、时间语义、版本与同步任务 |
| 身份设计 | 服务端身份校验、摘要存储、会话撤销方向正确 | 补当前账户状态、设备会话和退出契约；统一客户端状态 |
| 同步 | 幂等、删除抑制、失败不推进检查点是良好基础 | 补首次历史回填、更新策略、连接级锁和状态可见性 |
| 运维 | 有备份与恢复准备工具，但各入口不一致 | 单一发布入口、显式迁移、完整恢复演练、版本化发布 |
| 测试 | 覆盖多种隔离异常，但不能证明真实链路及设备可用 | 将本轮复现用例纳入回归，扩展前端 CI 和真实闭环验收 |
| 文档 | 历史详细，但当前规格分散且前后矛盾 | 建立当前导航、可验收规格和任务追踪，历史只作依据 |

- **P1：首个真实数据试用前应解决的正确性、权限或关键体验问题。**

## 3. 已有实现应保留的部分

1. 回忆查询以服务端内部 `user_id` 隔离，隐藏项默认不返回，时间加 ID 游标比 offset 更适合持续新增数据。
2. 高驰来源有唯一约束，重复导入不新增；删除抑制独立保存，普通同步不会自动恢复被删除项目。
3. worker 对疑似截断、非法时间、格式变化拒绝推进检查点，记录与进度一起提交；分段恢复保留已完成段。
4. 身份交换、绑定、会话、数据源与回忆职责基本分开；绑定校验已有账户密码；协调层用 SQLite 写锁串行化身份签发和撤销。
5. 新式会话不存明文令牌；解绑递增账户凭据代次；恢复准备工具撤销短期会话并生成新 JWT 密钥。
6. 页面明确标识虚构示例，历史记录明确标识模拟、只读联调、上传与发布的区别。

这些部分值得继续加强，不需要为了“更先进的架构”重做。

## 4. 具体问题与修改建议

### F01 · P0 · 部署暂停保护存在旁路

**证据：** `deploy/deploy.sh:7` 提前停止，但 `Makefile:80` 的 `deploy` 直接安装依赖、拉取代码和重启；`deploy/install-service.sh` 也能安装并重启服务。后两者没有调用完整迁移、备份恢复和回退流程。

**影响：** 开发者遵循历史说明运行 `make deploy` 仍可能在原地替换服务，绕过已设置的保护。不能把“一个脚本已停止”写成“所有部署入口已封闭”。

**建议：** T01 统一所有生产变更入口，未完成发布管理器前让旧入口明确停止。开发启动、安装服务、迁移、切换发布分别明确用途；正式发布只接受固定提交及已通过的检查结果。验收必须从每个旧入口验证，而非仅测试一个脚本。

### F02 · P0 · 备份入口仍使用不安全的直接复制

**证据：** `Makefile:101` 的 `backup` 使用 `cp` 数据库；`deploy/backup_sqlite.py` 已采用 SQLite 备份 API。两个入口行为不一致。

**影响：** 数据库处于活动写入、尤其 WAL 模式时，单独复制主文件可能漏掉已提交内容；存在一个正确脚本并不覆盖其他入口。

**建议：** 所有备份入口调用同一个快照组件。用保持 WAL 连接打开的样本证明最新提交包含在恢复副本中；对损坏、失败清理、权限和保留策略测试。后续媒体备份另有清单，不能以数据库备份替代。

### F03 · P0 · 默认测试入口可能触碰实际数据库

**证据：** `backend/tests/conftest.py` 在 fixture 替换数据库前导入 `main`；`backend/main.py:22` 在导入时执行 `create_all`；`backend/database.py:5` 默认相对数据库路径。`Makefile:73` 和 CI 未显式设置隔离数据库。

**影响：** 本地从后端目录运行默认测试时，可能在已有本地数据库建表；后续 fixture 隔离不能撤销导入阶段副作用。CI 临时环境与本地含真实数据库环境的风险不同。

**建议：** 测试启动前强制临时路径；应用导入不做 DDL。使用 app factory/显式配置和独立迁移命令；生产缺少明确数据库路径或 schema 版本不符时拒绝就绪。验收证明所有测试入口不修改仓库已有哨兵数据库。

### F04 · P1 · 导入旧导出文件可能复活后来删除的回忆

**证据：** `backend/services/data.py:79` 只要传入 `memory_suppressions` 就替换现有抑制集合；旧 v2 导出通常带空数组，导入时覆盖后续新增的删除标记。只有字段缺失的旧格式才保留当前抑制。

**本轮复现：** 在临时 SQLite 直接调用路由与服务：创建虚构来源回忆 → 导出 v2 → 删除 → 导入删除前的 v2。删除后回忆为 0、抑制为 1；导入后回忆为 1、抑制为 0。这里验证的是路由/领域行为，不是额外一次 HTTP 端到端复现。

**判断：** 如果产品定义为“回到历史快照”，这可能是预期行为；但现有接口没有区分恢复模式，也没有预告删除会被撤回，不能满足稳健的默认删除承诺。

**建议：** 默认导入采用合并并保留当前删除抑制，显式恢复被删内容另设预览和确认流程；整库灾难恢复是独立管理员流程。服务端预览必须展示新增、覆盖、冲突、删除恢复数量。版本字段必须参与解析，未知版本拒绝。

### F05 · P1 · 清空数据并不停止同步

**证据：** `backend/services/data.py:114` 删除回忆、抑制与检查点，未撤销来源连接或停止 worker；worker 默认从最近七天重新收集。

**影响：** 如果用户把“清空”理解为永久不再保存，下一次同步可能重新收录。当前尚未上线定时任务，但这是自动同步启用前必须解决的设计冲突。

**建议：** 区分“清空已收录内容并暂停来源”“继续连接并允许重新导入”“删除账户”。默认清空同时暂停来源；通过连接代次使在途任务提交失败。删除抑制不应因普通清空无条件丢失。

### F06 · P1 · 分页遇到 401 后仍显示旧私人记录，且加载状态悬挂

**证据：** `utils/api.js:45` 在 401 清除 token；`pages/river/river.js:104` 发现 token 改变后直接 return，既不清理私人内容也不复位 `loadingMore`。

**本轮复现：** 先加载 50 条虚构记录，再模拟分页请求清 token 并失败，最终 `mode=live`、50 条仍在内存、`loadingMore=true`。

**建议：** 用统一 auth generation 驱动页面。失效时立即清除私人列表/详情和加载状态，再至多恢复身份一次；恢复成功重新查询。普通网络错误可保留同一账户当前页，并明确提示更新时间。测试包含退出、换账号、401 与并发分页。

### F07 · P1 · 同一凭据下旧请求可覆盖新结果

**证据：** `pages/river/river.js:60` 只比较 token，未比较请求序号。两个同 token 请求乱序完成时都可写入页面。

**本轮复现：** 先发请求 A、后发 B；B 返回记录 2，A 随后返回记录 1；页面最终显示记录 1。

**建议：** 页面请求 generation + 账户 generation 双重校验；刷新和分页绑定同一个列表版本；卸载取消或忽略回包。验收还需覆盖刷新与旧分页交错，避免旧游标内容混入新列表。

### F08 · P1 · 来源可信度没有写入边界

**证据：** `backend/routers/memories.py:27` 接受 `MemoryCreate.source`；该 schema 允许客户端提交 `coros`。服务端没有限定只有连接器可创建供应商来源。

**影响：** 用户可把手写内容标成“来自高驰”，占用同账户来源 ID，使之后真实同步被去重跳过。这不是跨账户越权，但会破坏数据来源可信度。

**本轮验证：** 使用虚构账户直接调用创建路由，`source=coros` 和虚构来源 ID 被接受并写入临时数据库；未连接高驰。

**建议：** 普通写入 API 强制 `manual`；供应商写入只走内部 ingestion service。备份导入记录其导入来源和验证状态，不能凭客户端字段声称供应商已验证。

### F09 · P1 · 微信绑定状态与本机自动登录偏好混为一谈

**证据：** `pages/settings/settings.js:24` 把 `identity.enabled()` 作为 `wechatEnabled`；它读取本地布尔值。服务端无当前绑定状态查询；实验功能关闭时，已登录用户仍看到可操作的连接入口。

**影响：** 清理本地缓存、跨设备操作或服务端解绑后，界面可能显示错误状态。关闭本机自动识别并不等于解除服务端绑定。

**建议：** 增加 `/me`、功能能力和来源状态接口，分别维护服务端绑定、本机偏好、会话状态。能力未开通时提供明确说明；操作前后以服务端事实刷新。微信恢复应返回或随后获取当前用户资料，避免只有 token 没有账户显示信息。

### F10 · P1 · 密码与退出策略不一致

**证据：** `backend/schemas.py:9` 注册允许 4 字符，`pages/login/login.js:36` 登录和注册均拒绝小于 6 字符；JWT 默认 720 小时；设置页退出只清本机 token，不调用服务器撤销。

**影响：** 合法的已有短密码账户可能被前端挡住；退出后已复制的有效凭据仍能使用到过期或其他撤销发生。解绑撤销并不能替代常规退出。

**本轮验证：** `UserRegister` schema 接受四字符测试密码；前端六字符判断来自静态检查。未对任何真实密码或账户进行试探。

**建议：** 注册采用统一的新策略，登录兼容存量密码并提供升级路径；密码登录逐步统一到可撤销会话。区分退出当前设备、退出全部设备、解除微信绑定；新会话退出须服务端撤销。自用阶段默认关闭公开注册，已有账户引导优先。

### F11 · P1 · “偶遇”仅覆盖已加载列表

**证据：** `pages/river/river.js:115` 在 `data.memories` 中随机；首次仅最近 50 条。后端没有独立历史发现、日期导航或详情读取接口。

**影响：** 遗忘的旧日子很难被偶遇，核心体验退化为“最近记录随机切换”；用户必须先逐批加载旧记录。

**建议：** 提供独立发现 API，覆盖所有可见、允许偶遇的历史；首版用可解释的时间分层采样、短期去重，不引入机器学习推荐。日期跳转与普通列表作为稳定导航方式。

### F12 · P1 · 核心管理功能尚未落到小程序

**证据：** 回忆后端有创建、隐藏、删除，但客户端只暴露列表；页面没有文字补记、隐藏/删除、隐藏管理或日期跳转。不存在来源连接与同步状态页。

**建议：** 在高驰摘要试用前至少完成详情、来源状态、隐藏/删除与失败重试；文字补记纳入同阶段。把“知道为什么没有出现”“能决定不要再看到”作为自动采集功能的一部分。

### F13 · P1 · 首次同步不等于历史回填，更新和高密度日期无完整策略

**证据：** `backend/coros_worker.py:77` 首次仅最近七天；`--recover` 基于已有检查点补缺口；结果达到上限直接失败；`coros_sync.py:35` 冲突只忽略，不更新。锁绑定凭据目录，非数据库中的来源连接。

**影响：** 第一次使用缺乏老回忆；来源改名/修正无法传播；不同凭据目录可对同一账户来源并行执行；一次高密度返回可能持续阻塞。

**建议：** 显式历史范围任务，遇到上限自动缩短日期区间，单日仍满时标记覆盖不完整并停止，不谎报成功。连接级租约和 fencing generation；来源字段更新与用户笔记分离；失败退避、重授权和人工恢复都有可见状态。

### F14 · P1 · 高驰能力与适配契约需要重新核验

**证据：** worker 固定地区 issuer，文本解析器依赖 `LabelId/startTimestamp/SportType`；转换得到的 `sport_type` 没有落库。官方现行工具文档列出 FIT 下载与带配额的下载链接接口，历史“无 GPX 导出”不能推导成“完全无法得到运动轨迹”。[官方工具说明](https://github.com/coroslab/COROS-MCP/blob/main/docs/en/tools.md)

**建议：** 保存运动类型等后续详情定位字段；固定辅助程序版本与协议样本，验证真实响应结构、账户时区、区域路由和配额。官方设置页仍列地区地址作为回退，因此不能直接断言现有中国区地址失效。[官方连接说明](https://github.com/coroslab/COROS-MCP/blob/main/docs/en/getting-started.md)

FIT 路线作为增强项另行验证，摘要闭环不依赖它。引用的官方文档本次可读，但用户授权、历史覆盖和具体路线质量未实测。

### F15 · P1 · 媒体仍是纯文件原型，不能承接私人照片

**证据：** `photo_store.py` 只存字节和散列，未接 HTTP、媒体表或回忆关联；未验证图片内容、尺寸、EXIF、缩略图及事务一致性。

**建议：** 上传会话、完整校验、受控派生文件、媒体状态机和提交幂等一起做。文件落盘与 DB 分两阶段，崩溃后可对账；媒体读取认证和所有者校验不能依赖“随机 URL”。位置关闭时派生图和默认上传内容都不能暗带 GPS；原图保存选项单独说明。

### F16 · P1 · 安卓“选定相册”尚无系统权限与产品语义的对应验证

**证据：** `photo_sync_plan.py` 是纯内存集合过滤，没有 Android 工程、权限管理和持久队列。Android 的选定照片授权、目录授权、逻辑相册并非同一概念。[选定照片访问](https://developer.android.com/about/versions/14/changes/partial-photo-video-access)；[目录授权](https://developer.android.com/training/data-storage/shared/documents-files)

**建议：** 先做目标手机上的最小验证：能否只读选定相册、是否包含后来新增照片、重启与撤销后如何表现。再决定 MediaStore+应用内相册白名单或受限目录授权；单次 Photo Picker 用于手动添加，不能将选中照片包装成持续授权整个相册。后台用 WorkManager 配合条件与重试，保留“立即同步”。[任务调度](https://developer.android.com/develop/background-work/background-tasks/persistent)

### F17 · P2 · 数据模型欠缺时间、来源连接与媒体语义

**证据：** `Memory` 主要为来源 ID、UTC 字符串、文本与隐藏；`SyncState` 只有最后成功日期。前端用设备时区格式化，未保留事件原始时区、日期精度、来源更新时间、连接 ID、媒体及用户备注。

**建议：** 最小增量迁移，保留 UTC 排序，同时补来源时间与精度；照片无拍摄时间时显示“时间待确认”，不能静默把上传时间当拍摄时间。唯一键将来按来源连接作用域定义；迁移前核实供应商 ID 是否全局唯一。外键/业务约束分阶段补，迁移先查历史孤儿记录。

### F18 · P2 · 前端列表增长和状态表达欠缺规格

**证据：** 时间线为全部加载记录生成按钮；`setData` 反复传全量数组；每次 `onShow` 重载首屏，可能丢失浏览位置；普通请求失败回退示例。

**建议：** 有界页面缓存、增量更新、保留浏览锚点；大历史按日期窗口导航。区分未连接、空库、加载、部分失败、授权失效；同账户临时网络故障保留当前真实结果并标陈旧。身份失效则清屏，两者不可混同。

### F19 · P1 · CI 未覆盖关键变更路径

**证据：** `.github/workflows/ci.yml` 主要由 `backend/**` 触发，只运行 pytest；`pages/`、`utils/`、`tests/`、`deploy/`、`Makefile` 的独立变更不能获得完整验证。部署脚本变更也可能不触发。

**建议：** 一条清晰 CI 同时执行隔离后端测试、五组 Node 测试和配置校验；部署文件变更触发备份恢复与发布门禁测试。保留真实设备与供应商联调记录，不能声称 CI 覆盖了它们。

### F20 · P1 · 健康检查不能用作可靠发布就绪判据

**证据：** `backend/main.py:135` 即使 DB 检查失败仍返回 HTTP 200 与顶层 `status=ok`；查询只执行 `SELECT 1`，不验证 schema 版本或关键配置。静态运行预检也未接入所有启动入口。

**建议：** liveness 与 readiness 分开；数据库/schema/必要配置不满足时 readiness 返回 503；外部供应商故障独立显示来源降级，通常不使全部回忆读取停机。请求 ID 统一生成、限制长度并在日志和错误体一致关联，不记录内容和凭据。

### F21 · P2 · 导入导出尚不是完整可恢复的产品能力

**证据：** `ImportData` 未声明/校验导出 `version`，旧业务列表为未类型化 List；导入先清空账单/健身；导出全量 `.all()` 再整体 JSON；设置页写出文件无明确清理生命周期。

**建议：** 数据导出与系统备份分别命名；建立版本化 manifest、类型校验、导入预览和资源上限。照片阶段导出包含媒体清单与校验值；大导出异步或分批；导出文件私有、有效期明确、退出与到期清理。平台文件保存能力须真机验证，避免把应用内保存文案写成已存系统相册。

### F22 · P2 · 文档与代码状态相互漂移

**证据：** README 有历史提示但主体仍为旧产品；CLAUDE.md 仍描述 13 页及旧模块系统；《首版方案》仍写保留旧入口，用户后续已选择移除；身份架构和部分模块注释仍说未接 HTTP，但代码已接入。

**建议：** 以本轮导航建立当前入口；后续 T01 更新 README、开发说明和旧文档状态标识，保留历史事实不覆盖。每项需求关联验收和任务，提交说明记录是否部署。

### F23 · P2 · 运行可观测性和容量计划不足

**证据：** SyncState 无失败原因、尝试时间、覆盖区间和积压；SQLite 写锁承担身份、限流和同步，暂无容量/争用基线；worker 捕获子进程全部输出后解析，只有时间限制，没有输出字节上限。

**建议：** 保存脱敏任务状态、覆盖范围和固定错误码；增加输出/文件/导入上限、限流桶与旧会话清理。定义慢请求、锁冲突、磁盘、水位、备份年龄与恢复耗时指标。先实测单机，不凭想象迁移 PostgreSQL。

### F24 · P2 · 配置与公开仓库治理需持续检查

**证据：** API 地址硬编码，开发与生产配置缺少统一边界；`project.private.config.json` 已被 Git 跟踪；`.gitignore` 的 `*.db` 不覆盖所有 WAL/SHM 或其他数据库后缀。依赖固定了顶层版本，但缺少完整依赖审计和可复现构建证据。

**建议：** 配置注入、版本显示与能力协商分开；确认后将个人配置迁出版本管理并保留本机文件，不能覆盖当前用户修改。增加凭据/数据库伴随文件扫描和构建产物检查。审计公开历史时不在报告复制命中值；若发现真实秘密，再走轮换流程。此处不宣称已发现密钥泄露或已确认依赖漏洞。

## 6. 验证记录

本轮完整后端隔离回归 **107 项通过，耗时 55.85 秒**；五组 Node 模拟测试全部通过。测试环境为临时 Python 3.12 虚拟环境，已有 CI 指定 3.11，本轮没有额外验证 3.11。共 292 条弃用警告，涉及 datetime.utcnow、Pydantic Config、Passlib crypt 和 AnyIO 别名，后续依赖升级时处理，不能把警告计为测试失败。

沙箱内 Starlette TestClient 启动停在 AnyIO 线程桥接等待，最小健康检查在 15 秒超时。停止挂起进程后，同样显式使用 `/tmp` 数据库和测试密钥在获准的沙箱外环境完成回归；因此本轮不将该挂起列为产品缺陷。

额外验证结果：

| 检查 | 方法 | 结果 |
|---|---|---|
